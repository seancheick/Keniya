# Checkout reservations

Apply the commerce migration before enabling checkout. Configure Stripe delivery for checkout completion, expiration, refunds, and dispute updates; failed persistence intentionally returns HTTP 500 for retry.

Capacity counts paid/non-refunded orders and every unconsumed, unreleased reservation. Passing the reservation's expiry time does **not** release capacity: a buyer may have paid just before expiry while Stripe's webhook is delayed. Checkout requests reconcile expired reservations that have a Stripe session ID, releasing only sessions Stripe currently reports expired and unpaid. The signed expiration webhook uses the same check.

A Stripe timeout or database binding failure can leave a reservation without a session ID. Once five minutes have passed after expiry, checkout reconciles it by fully listing Stripe sessions created during the reservation window and matching its metadata. A confirmed absent session releases the hold; a paid session is rebound and retains capacity. Listing failures or more than 100 pages retain capacity for investigation. Do not release it merely because it is old. In Stripe, identify the session whose metadata `reservation_key` matches the database `request_key`; bind that session ID. If paid, retry its completion webhook to durably save the order. If expired and unpaid, release the matching reservation after verifying Stripe's current state. If no matching session can be established, retain the hold and investigate Stripe request logs using `checkout:<request_key>` as the idempotency key. This conservatively reduces availability rather than overselling.

Public catalog requests and checkout requests perform reconciliation; no background worker or scheduled cleanup is installed. If neither catalog nor checkout requests arrive, holds remain conservatively occupied until a request or operator reconciliation. Partial refunds and active/lost disputes keep capacity occupied but block fulfillment; full refunds free capacity. An existing fully refunded order is never changed back to paid by a repeated checkout completion.

## Legacy recovery links and admission holds

Expired Stripe recovery links created by earlier versions may remain redeemable even after the app stops publishing them. A payment is never treated as an admitted preorder solely because Stripe reports it paid. `save_paid_order` records the payment and verifies the exact session against its unreleased, non-invalidated reservation with stored admission inputs. Missing reservations, recovered session mismatches and invalidated reservations receive `admission_hold`; the customer receives no reserved-box confirmation and planning, packing and shipping remain blocked. Admission provenance is immutable. Refund/dispute synchronization cannot change an unverified payment back to `paid`. Existing paid rows without provenance are quarantined during migration.

For an admission hold, inspect the Stripe session/payment and reservation history. Contact the buyer through the operator's normal process and arrange a manual refund when the purchase cannot be honored under current rules and capacity. If review establishes a different remedy, record it separately; do not change immutable provenance or mark the quarantined order paid to bypass fulfillment safeguards. No automatic refunds are performed. A fresh purchase must use the normal box page and obtain new admission.
